Case Studies

Three systems, three different answers.

The same engineer, three deliberately different architectures. Each choice came from the operating conditions, not from preference.

Community / Platform

Heartlynks Community

A social platform where one action fans out into many downstream effects.

Problem

In a community product, a single post triggers feed updates, notifications and counters for an unpredictable number of other users. Doing that work inside the request means the person posting waits for everyone else's bookkeeping.

What was built

A Go service on Fiber handles the HTTP path and does only what the caller needs. Everything downstream is published to Kafka and consumed independently, so a slow or failing consumer never blocks a write.

Why these choices

Go for predictable memory and concurrency under fan-out. Kafka because the events are worth replaying and the consumers will keep multiplying. PostgreSQL for relational integrity, Redis for the reads that repeat.

Automation / SaaS

The Automate

Scheduled, long-running work that must not be tied to whoever opened the browser.

Problem

Automation jobs run on their own schedule and can outlive any session. A user configures a workflow once and expects it to keep running whether or not anyone is watching.

What was built

A NestJS API that owns scheduling, execution and job state, deliberately separated from the Next.js client. The interface configures work; it never performs it. Redis carries queueing and the state that jobs check between runs.

Why these choices

A split API rather than a monolith, because the execution surface has a different lifecycle from the UI and needs to scale and be restarted on its own terms. NestJS for the module structure — job definitions multiply fast, and this keeps that growth navigable.

HR / Workforce

Lifeguard HRMS

A web application with a second client that isn't a browser.

Problem

Workforce productivity data originates on employee machines, not in a web session. That means an ingest path with different assumptions: intermittent connectivity, unattended clients, and data that must not be lost when the network drops.

What was built

A Laravel application serving a Vue interface for HR staff, plus a separate authenticated ingest surface for the desktop monitoring agent. The two clients share a domain model but almost nothing else.

Why these choices

A Laravel monolith because one team maintains it and the domain is relational throughout — employees, attendance, payroll periods. Splitting it would have added operational cost with nothing to buy. Monitoring data is sensitive, so the agent's surface is isolated and separately authenticated.

How I Engineer

Four things I hold to.

01

Architecture follows the problem.

Not the framework, not the trend, not what I used last time. Microservices for a three-person team are a tax with no return. A monolith under genuine fan-out is a bottleneck. The operating conditions decide, and they're different on every project.

02

Production is part of the product.

Code that works on a laptop is half a deliverable. Containers, environments, secrets, releases and rollbacks are engineering, not an afterthought handed to someone else. I ship it and I run it.

03

Simple systems are usually better systems.

Every moving part is a thing that fails at 2am and a thing the next engineer has to learn. I add distribution, caching and queues when the load justifies them — and I can tell you what specifically justified each one.

04

I build for the team that inherits the code.

Most software outlives the person who wrote it. In ERP and CRM work especially, the hard part is understanding the process a company already runs on paper or in someone's head, and deciding what to keep. Software that contradicts how a business works gets abandoned, however well it's built.

AI & Automation

AI that fits into real products.

Most AI work I do isn't a new product. It's a step removed from an existing one — a form someone was filling by hand, a queue someone was triaging, a report someone was assembling on Friday afternoons.

That means the interesting engineering is rarely the model call. It's what happens around it: validating output before it touches a database, handling the cases the model gets wrong, and making the whole thing legible to the team that has to trust it.
