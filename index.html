How I work

Over ten years I've moved between interface, server and infrastructure rather than settling into one of them. That was deliberate. Most of the problems worth solving in business software sit at the seams — between the client and the API, between the API and the database, between the code and the machine it runs on — and those seams are invisible if you only ever work on one side.

It also means I pick the stack for the job rather than the job for the stack. A CRM that one small team maintains is better as a Laravel monolith with Inertia than as a split API and client, because there is no second team to justify the split. A community feed with unpredictable load is better in Go with Kafka carrying events between services. I've shipped both, and the reasoning was the same each time: choose what the people who inherit it can actually operate.

I deploy and run what I build. Containers, AWS and Google Cloud, managed hosting where the simpler thing is the right thing. Handing over a repository and calling it finished has never been the job.
